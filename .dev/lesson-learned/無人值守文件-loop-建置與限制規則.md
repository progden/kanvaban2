# 無人值守文件 loop — 建置與限制規則

> 目的：把 `spec-migration-loop`、`ui-authoring-loop` 兩個既有 loop 共用的建置方式與限制規則收斂成可複用的樣板，供之後新開 loop（例如遷移剩餘模組、或未來的 `design-*.md` 撰寫 loop）直接套用，不必重新摸索一次。
> 適用位置：`.dev/loops/<name>-loop/`；具體規則本體見各 loop 自己的 `*-prompt.md`（本檔只講「為什麼這樣搭」與「共同鐵則」，不覆蓋各 loop 的領域規則）。

## 1. 實體

| 實體 | 定義 | 關鍵屬性 |
|---|---|---|
| 規則書 Prompt（`<name>-prompt.md`） | 不隨進度改變的鐵則來源，執行輪／審查輪共用 | 角色、目標、檔案地圖、鐵則、自主決策分級 |
| 執行輪 Kickoff（`<name>-kickoff-prompt.md`） | 一輪流程：讀什麼、做什麼、怎麼收尾 | 讀取清單、收尾檢查清單 |
| 審查輪 Review（`<name>-review-prompt.md`） | 唯讀審查流程，只能追加 `D-xx` 或審查紀錄 | 審查對象、可追加的產出 |
| 任務清單 Ledger（`<name>-tasks.md`） | 唯一任務來源 | 狀態（`todo`／`doing`／`done`／`blocked`／`proposed`／`rejected`）、依賴、驗收條件 |
| 任務 Task（`T-xx`／`G*`／`D-xx`） | 任務清單裡的一列 | `T-xx` 人工排定；`G*` 關卡；`D-xx` 執行輪或審查輪發現的計畫外工作 |
| 執行日誌 PDCA（`<name>-pdca.md`） | 只能追加的執行紀錄 | 每則含 Plan／Do／Check／Act |
| 狀態快照 State（`<name>-state.md`） | 每輪覆寫、20 行內 | 給下一輪（zero context）快速回復現況 |
| 審查紀錄 Review Log（`<name>-review.md`） | 只能追加 | 審查發現、關卡核准與否 |
| 待確認事項 OQ（`<name>-open-questions.md`） | 只能追加，高風險假設集中地 | Level 標記、情況（四選一）、選項、逐字引用 |
| 外部驗證腳本（`verify-<name>.sh`） | 每輪結束後跑，**不採信 agent 自己的回報** | 讀 `runtime/last-verify.md` 判定 PASS／FAIL |
| 驅動腳本（`run-<name>-loop.sh`） | 自動模式的外層迴圈，全新 `claude -p` process | 環境變數、停止條件、gate 自動核准 |
| 執行期檔案 Runtime（`runtime/`，不進版控） | `baseline`／`errors.json`／`gates/`／`logs/`／`DONE`／`state` | 只有腳本能寫；agent 只能建立 `DONE` |

## 2. 關係

| 關係 | 主詞 → 受詞 | 數量約束 |
|---|---|---|
| `governs` | 規則書 Prompt → 執行輪／審查輪 | 1 對多，鐵則來源只有一份 |
| `selects` | 驅動腳本 → 任務 | 依 `doing` → `D-xx` 的 `todo` → 表格順序第一個依賴全 `done` 的 `todo`，1 輪選 1 個 |
| `blocks` | 關卡 `G*` → 後續任務 | 審查沒有待修 `D-xx` 才能核准；核准前後續任務不可執行 |
| `verifies` | 外部驗證腳本 → 執行輪產出 | 每輪必跑，FAIL 時下一輪必須先修正，不看 agent 自稱「完成」 |
| `proposes` | 執行輪／審查輪 → `D-xx` | 狀態固定 `proposed`／`todo`（依 loop 而定），**不可自行開工** |
| `escalates` | 高風險判斷 → OQ | 1 對 1，同時在對應文件標 `⚠️` 並指向該 OQ |
| `records` | 執行輪 → PDCA | 每輪至少一則，只能追加 |

## 3. 跑法：`run-<name>-loop.sh` 驅動的自動模式

兩個 loop 的規則書都寫了「手動模式（`/loop`）／自動模式」兩種跑法，但實際只跑過自動模式——`run-<name>-loop.sh` 驅動：每輪全新 `claude -p` process（zero context），執行輪與審查輪交替（`REVIEW_EVERY` 或遇關卡），每輪結束外部驗證腳本判定通過與否，`--dangerously-skip-permissions` 才能無人值守 commit，適合跑完整批次工作量（例如六個模組）且無人值守。手動模式只是規則書裡的備案寫法，未實際使用過，本檔不收錄。

**必須先在專用分支（`loop/<name>`）執行**，main 不受影響，壞了可整支丟棄；啟動前腳本會檢查工作區乾淨、`scripts/tests` 先過。

## 4. 執行模型：輪次與關卡

| 輪次 | 觸發 | 模型／effort | 能做什麼 | 不能做什麼 |
|---|---|---|---|---|
| 執行輪 | 預設 | 較弱模型／medium（Sonnet） | 完成任務清單裡「一個」actionable 任務；可追加 `D-xx` | 不能自行開工 `D-xx`；不能碰下一個任務 |
| 審查輪 | 每 `REVIEW_EVERY` 輪、或遇到 `G*` 關卡前 | 較強模型／medium（Opus） | 唯讀規格與產出，只能追加 `D-xx` 修正任務或審查紀錄 | 不能改規格／產出本體 |
| 關卡 `G*` | 任務清單排到 `G*` | 腳本判定 | 先跑審查輪；審查沒有留下待修 `D-xx` 就自動核准（建 `runtime/gates/<G>.approved`），同一關卡審查達 `GATE_MAX_REVIEWS` 次後直接核准；`AUTO_APPROVE_GATES=0` 則停下等人工建核准檔 | — |

**不變量**：核准檔（`runtime/gates/*.approved`）的時間必須早於下一輪開始時間，否則驗證腳本視為 agent 偽造核准。

## 5. 自主決策分級（兩個 loop 共同結構，內容依領域不同）

每輪都是重新讀檔案（zero context），遇到不確定時**不停下、不等人類回答**，依風險分級處理：

| 等級 | 判斷依據 | 做法 |
|---|---|---|
| 低風險 | 純呈現、命名微調、不影響已定案內容 | 自行決定，PDCA 記一句話，繼續做 |
| 高風險 | 來源文件沒寫清楚的規則／欄位／範圍找不到依據 | 標 `⚠️` 寫進產出的「待確認事項」，**該產出狀態不得標「已定案」**；同時在 OQ 表追加一列，產出裡的待確認事項指向它 |
| 覆蓋來源 | 新答案跟已定稿的來源內容（Scenario、名詞表、usecase 區塊等）**不一致**，不是補空白而是要動到定稿文字 | **禁止直接依新答案改動產出、更不能改來源文件本身**；用【覆蓋】格式明示「原文『逐字引用』→ 若採用新答案，需改為『新文字』」；產出維持照舊來源寫，任務標 `blocked`；這是結構性改動，必須先走 CR 流程，loop 不能替代這個決策 |
| 環境限制 | 來源文件本身有落差（例如某條目完全沒有可推導的依據）、檢查腳本跑出非預期錯誤 | OQ 記錄＋任務標 `blocked`，只有人工能解除 |

判斷不出等級一律視為高風險；判斷不出是「高風險」還是「覆蓋來源」一律視為「覆蓋來源」——**寧可多擋一次人工確認，也不要靜默改掉已定案內容**。這是兩個 loop 唯一共通、且最重要的一條鐵則。

OQ 記錄格式的不變量（沿用 `.dev/lesson-learned/與專家協作的提問規則-本體論分析.md` 的主體 A／B／C／E）：

- 情況欄只能是「引用原文」「兩處矛盾並列」「推論＋所本原文」「覆蓋」四選一並標明種類，逐字引用一律用『』包住，不用「應該」「我認為」「比較好」等說服性字眼代替引用。
- 矛盾類固定給「保留A／保留B／缺區分條件」三個選項。
- 每列開頭固定加 `[Level: <模組>/<uc 或條目 ID>]` 標記。
- 選項牽涉挑既有類別（角色、Use Case、Screen 等）時要列出該類別**完整清單**，不能只列 loop 想到的兩三個。
- 新增前先查重（既有 OQ 表、已完成產出裡的「待確認事項」），要推翻先前結論須明講「推翻 OQ-xx」並說明差異。

## 6. 檔案權限矩陣（MECE，兩個 loop 都用這個三分法）

| 分類 | 目錄 | 誰可以改 |
|---|---|---|
| 不變規則 | `prompts/`（或 loop 根目錄的 `*-prompt.md` 等） | 人工 |
| 累積紀錄 | `.state/`（任務清單、PDCA、審查、OQ、狀態快照） | loop 依表格個別規則（大多只能追加或改狀態欄，任務描述／驗收條件／依賴只有人工能改） |
| 輔助腳本 | `scripts/`（工具、外部驗證、逐字引用驗證等） | 人工；loop 只能「執行」，不能「修改」 |
| 執行期檔案 | `runtime/`（不進版控） | 腳本／loop；`DONE` 是 loop 唯一能建立的完成訊號 |
| 產出對象 | 例如 `.dev/F0x-*/spec-*.md` 或 `ui-*.md` | loop（執行輪） |
| 上游依據＋規範＋既有腳本 | 來源規格、`.dev/conventions/**`、`scripts/**`、`CLAUDE.md`、`design-*.md` | **不可修改**：缺什麼標 `⚠️` 回饋，不自己補；發現腳本本身有 bug 記 OQ，不修腳本 |

## 7. 外部驗證與停止條件

- 每輪執行輪結束，`verify-<name>.sh` 做**外部**驗證（重新跑檢查腳本、比對 diff 範圍、核對任務清單格式），寫入 `runtime/last-verify.md`；不採信 agent 自己宣稱「完成」。
- 停止條件（四選一，驅動腳本印出原因）：
  1. 出現 `runtime/DONE`（完成）。
  2. 達 `MAX_ITERATIONS`（尚未完成，人工檢查）。
  3. 沒有可執行任務（全部 `blocked`，或 `AUTO_APPROVE_GATES=0` 時卡在等人工關卡）。
  4. 同一任務連續驗證失敗 `MAX_TASK_FAILS` 次，或連續 `MAX_NO_PROGRESS` 個執行輪沒有前進（任務狀態沒變、error 數沒下降）。
- 人工介入後，把任務改回 `todo`（或建核准檔）即可用同一指令接續，`runtime/` 保留跨輪狀態，已完成的任務不會重做。

## 8. commit 規範（兩個 loop 一致的分類方式）

| 改動對象 | 訊息前綴 |
|---|---|
| 產出本體（spec／ui 等） | `[spec/design](<scope>) <摘要>` |
| loop 自己的任務清單／PDCA／OQ／審查紀錄 | `[docs](loops) <摘要>` |

兩類改動分開 commit；只 `git add` 本輪修改的檔案；不 `git push`；`<scope>` 用小寫英文與連字號（`git-convension.md` 限制），不可用 `F0x` 編號。

## 9. 禁止事項（兩個 loop 共同的紅線）

- 定義來源文件沒有的新概念／改寫來源文件正文、更不能改 `.dev/conventions/**`、`scripts/**`、`CLAUDE.md`。
- 為了讓檢查腳本通過而刪減段落、亂填「不適用」掩蓋真正缺的資訊，或把「討論中」硬標成「已定案」。
- OQ／待確認事項用「應該」「建議這樣比較好」「我認為」等說服性字眼取代逐字引用。
- 向使用者提問、等待人工回覆（zero-context loop 的前提就是不能等）。
- 一輪做多個任務、提前做下一個任務、自行發明或改寫任務清單裡既有任務的描述／驗收條件／依賴（只能追加新的 `D-xx`）。
- 在背景執行指令後就結束回合（一輪必須真正跑完驗證再收尾）。

## 10. 新開一個 loop 時的檢查清單

1. 依第 6 節建三個子目錄（`prompts/`／`.state/`／`scripts/`）＋ loop 根目錄的驅動腳本＋ `runtime/`（加進 `.gitignore`）。
2. 規則書（`*-prompt.md`）至少要有：角色、目標、檔案地圖（含「誰可以改」）、鐵則（對應該領域的 MECE 邊界）、第 5 節的自主決策分級表、commit 規範、禁止事項、收尾條件、自動模式操作手冊。
3. 任務清單第一則規則段要講清楚：狀態值定義、挑選順序、`G*` 關卡怎麼核准、驗收條件裡機械條件怎麼被 `tools accept-check` 判定。
4. 外部驗證腳本至少要查：檢查腳本 error／warn 數（起點 vs 現在）、diff 範圍是否只動了允許的檔案、任務清單格式是否合法、（若有）逐字引用是否與來源相符。
5. 驅動腳本沿用 `run-spec-migration-loop.sh`／`run-ui-authoring-loop.sh` 同構：事前檢查（工具、工作區乾淨、測試先過）→ 切分支 → 記 baseline／起點 error 數 → 主迴圈（選任務→判斷 exec/review/gate→組 prompt→`timeout claude -p`→外部驗證→更新跨輪狀態→判斷停止條件）。直接以自動模式為主要跑法即可，不必額外準備手動模式的操作手冊。
6. 別忘了把 `runtime/`、`__pycache__/` 加進 `.gitignore`，並在規則書「檔案地圖」明講「不進版控」。
