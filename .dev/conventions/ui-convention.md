# UI 短規格撰寫規範（UI Convention）

## 定位

這份 Convention 描述的是「後端 Spec 已經存在」之後的工作：把 Spec 裡的 Feature 拆成畫面，逐一和使用者討論出每個畫面的**短規格**，寫進 `ui-<模組>.md`，最後產出可以直接貼進 Claude Design 的提示詞。

它刻意只管兩件事：

1. 畫面**該有什麼**（資訊架構、狀態、資料、操作）。
2. 畫面**不該由 Design 自己猜什麼**。

畫面長什麼樣（排版、間距、元件選型、視覺風格）不在這份文件裡，那是 Claude Design 的工作，也是它做得比人快的部分。短規格寫到「Design 猜不到的東西」就停，剩下的用看的收斂。

`ui-<模組>.md` 跟 spec 一樣會被腳本（`ui-check`）解析：它只能**引用** spec 檔已定義的 ID，不能自己定義實體、Use Case 或角色。畫面需要而 spec 沒有的東西，標 `⚠️` 回饋後端 Spec，不在 ui 檔裡補。

同目錄的 `design-<模組>.md` 記錄系統內部實作決策（API 契約、資料模型、交易邊界），依 `design-convention.md`（待撰寫），不被腳本解析、不進 CR 影響 ID。

spec / ui / design 的責任邊界見 `docs-convention.md` 第 2 節。

## 你的角色

你是負責 UI 規格的系統分析師。規格的所有權在使用者身上，你負責的是：從後端 Spec 推導出畫面清單、用提問把每個畫面缺的資訊補齊、把結果整理成短規格。你不替使用者做產品決策，但你要主動指出 Spec 和畫面之間對不上的地方。

## 輸入：後端 Spec

開始前先讀完 `spec-<模組>.md`，從裡面抓出四類資訊，之後每個畫面的討論都建立在這上面：

| 抓什麼 | 在 spec 的哪裡 | 用在哪 |
| --- | --- | --- |
| Feature 清單與所屬模組 | `## Feature:` 標題 | 決定有哪些畫面、畫面歸哪個模組 |
| Use Case 清單（`uc-` ID、`roles`、`crud`、`pre`／`post`／`fail`） | 每個 Feature 的 `### Use Case 定義` | 每個畫面對應哪些讀／寫操作；操作的成功後／失敗時直接從 `post`／`fail` 推 |
| 資料結構（實體、欄位、型別、限制） | `## 名詞定義` 三張表 | 畫面要顯示、輸入哪些欄位；驗證規則從欄位表的「限制」欄來 |
| 角色與權限 | `## 角色定義` + usecase 的 `roles` | 畫面有哪些角色差異、誰做得到什麼 |

Spec 裡沒有的資訊不要自己補。缺的部分標 `⚠️ 待確認`，在畫面討論時一併問。

Feature 名稱、模組編號（F01…）沿用 spec 與目錄名，不另起一套命名。

## 流程

### 第一步：畫面盤點

先不要進任何單一畫面，先列出整份 Spec 會產生哪些畫面，讓使用者確認範圍。盤點結果直接寫成 `ui-<模組>.md` 裡每個畫面的標題與前三行（所屬 Feature、類型、狀態），內容段落先留空。

**畫面總表不再手寫**：`ui-check --report` 會從 ui 檔即時印出總表（Screen ID、名稱、所屬 Feature、類型、觸發的 Use Case、狀態），討論時用它看進度。

畫面類型固定用這幾種，方便之後的提問有針對性：**列表、詳情、表單、儀表板、流程（多步驟）、對話框／側欄、設定**。一個畫面裡的對話框或側欄如果有自己的資料與操作，獨立成一個畫面；只是確認訊息就併入母畫面。

盤點時主動做兩個對照，發現落差就列出來給使用者（`ui-check` 也會以 warn 回報前者）：

- **寫入 Use Case 沒有任何畫面的操作表引用** → 問：這是背景作業、由事件觸發，還是漏了畫面？
- **畫面需要的欄位 spec 欄位表沒有** → 標 `⚠️`，回饋給後端 Spec。

狀態只有三種：未討論 → 討論中 → 已定案。使用者說「先跳去看 `s-swimlane-delete-dialog`」就跳，總表負責記住哪些還沒回來。

### 第二步：逐一討論短規格

每個畫面走同一個循環：

1. **草擬**：依據 Spec 先填一版短規格，能從 Spec 推出來的直接填，推不出來的標 `⚠️ 待確認`。不要為了版面好看把空格填滿。
2. **提問**：針對 `⚠️` 一次最多 3–5 題，依優先序分批。每題附一句「為什麼問這個」。
3. **更新**：使用者回覆後更新短規格，把回答直接寫進對應段落，而不是另外記在對話裡。
4. **收斂**：`⚠️` 清空、驗收條件可以逐條對照畫面、`ui-check` 無 error，就標「已定案」。

使用者表態「你決定就好」的項目，改成**給 2–3 個選項讓他選**，並說明各自的取捨；不要繼續追問，也不要悄悄自己決定。

### 第三步：產出 Design 提示詞

畫面定案後，把短規格整理成一段可以直接貼進 Claude Design 的提示詞（格式見文末）。一個畫面一段，同一個 Feature 的畫面可以合併成一次貼上，讓 Design 看到畫面之間的關係。

## 檔案與固定格式

| 項目 | 規則 |
| --- | --- |
| 檔名 | `ui-<模組>.md`，`<模組>` 與對應的 `spec-<模組>.md` 相同，放同一個目錄 |
| 檔頭 | `# <模組名稱> UI 短規格`，一段簡介，註明對應的 spec 檔 |
| 畫面標題 | `## s-<id>：<畫面名稱>`，全形冒號；`s-<id>` 是 Screen ID（小寫英文、數字、連字號，全專案唯一） |
| 畫面標題下三行 | `所屬 Feature：<Feature 名稱>`、`類型：<七種之一>`、`狀態：未討論／討論中／已定案` |
| 段落標題 | 固定字串、固定順序、每個畫面八個都要有：`### 目的`、`### 進入與離開`、`### 角色與權限`、`### 資料`、`### 操作`、`### 狀態`、`### 驗收條件`、`### 待確認事項` |
| ID 引用 | 所有 Entity／Attribute／Role／UseCase／Event／Screen ID 一律反引號包住，規則同 `spec-convention.md` 第 9 節；反引號裡只放 ID |
| 不定義新東西 | ui 檔不出現 spec 沒有的實體、欄位、角色、Use Case；需要就回饋 spec |

## 短規格模板

**格式範例**（`ui-kanban-basic.md` 中的一個畫面，沿用 CR-024 情境；引用的 ID 均定義於 `spec-convention.md` 第 2 節的範例）：

```markdown
## s-swimlane-delete-dialog：刪除 Swimlane 對話框
所屬 Feature：Swimlane 管理
類型：對話框
狀態：已定案

### 目的
看板管理者在刪除仍有卡片的泳道時，指定卡片要移去哪個泳道。

### 進入與離開
- 從哪裡進來：`s-swimlane-list` 的「刪除」操作，且該泳道內有卡片
- 完成後去哪裡：回到 `s-swimlane-list`，列表重新載入
- 中途放棄會怎樣：關閉對話框，泳道與卡片不變

### 角色與權限
| 角色 | 看得到 | 做得到 |
|---|---|---|
| `r-board-admin` | 全部 | 選擇目的泳道、確認刪除、取消 |
| `r-member` | 不會進入此畫面 | 無 |

### 資料
| 欄位 | 來源 | 顯示 / 輸入 | 驗證 / 格式 | 說明 |
|---|---|---|---|---|
| 泳道名稱 | `swimlane.name` | 顯示 | — | 要刪除的泳道 |
| 卡片數 | `swimlane`→`card` 關係計數 | 顯示 | — | 提示使用者有幾張卡片會被移動 |
| 目的泳道 | `card.swimlane` | 輸入（單選） | 必填；不可選到自己 | 選項為看板內其他泳道 |

### 操作
| 操作 | 觸發 | 成功後 | 失敗時 | 需確認？ |
|---|---|---|---|---|
| 確認刪除 | `uc-delete-swimlane` | 關閉對話框，回列表 | 依 `uc-delete-swimlane` p2：保留對話框與已選項目，顯示訊息 | 是（本畫面即確認） |
| 取消 | — | 關閉對話框 | — | 否 |

### 狀態
- 載入中：載入其他泳道清單時顯示
- 空資料：不適用（進入此畫面代表看板至少有兩個泳道）
- 錯誤：儲存失敗時保留對話框與已選項目，顯示錯誤
- 無權限：不適用（無權限者不會看到刪除操作）
- 資料狀態差異：不適用

### 驗收條件
- 目的泳道下拉不含被刪除的泳道本身
- 未選目的泳道時確認按鈕不可送出，且顯示固定錯誤訊息
- 成功後回到 `s-swimlane-list` 且列表重新載入

### 待確認事項
- （無）
```

### 各段落怎麼填

**目的**：只寫一句，寫不成一句通常代表這個畫面該拆成兩個。

**進入與離開**：這段決定導覽結構，Design 猜錯這裡會整個資訊架構歪掉。提到其他畫面時用 Screen ID（反引號），腳本會檢查它存在；模組入口畫面（沒有任何畫面會導向它的）在「從哪裡進來」寫「模組入口」。多步驟流程要寫清楚每一步之間能不能回頭。

**角色與權限**：`角色` 欄填 Role ID。從 spec 的角色表與 usecase 的 `roles` 推：畫面上某個操作觸發的 Use Case，其 `roles` 要跟這張表「做得到」該操作的角色一致（腳本檢查 DS-05）。同一個畫面不同角色看到的差異如果很大，考慮拆成兩個畫面。

**資料**：欄位清單直接對照 spec 的欄位表，`來源` 欄填 Attribute ID（反引號），讓交接時前端不用猜 mapping；衍生值（計數、合計）寫出它由哪個關係或欄位算出來，並把用到的 ID 反引號包住。驗證規則從欄位表的「限制」欄抄過來，spec 沒寫的標 `⚠️`。列表畫面另外寫清楚：預設排序、可篩選欄位、分頁還是無限捲動、預估筆數。

**操作**：每個會觸發 Use Case 的按鈕都要有一行，`觸發` 欄填 UseCase ID（反引號）；純前端操作（取消、關閉）`觸發` 欄填 `—`。「成功後」對應 usecase 的 `post`。「失敗時」欄只寫呈現方式（保留對話框、顯示訊息、回到哪個畫面），業務結果與資料狀態不重述，以「依 `uc-xxx` p2」引用 usecase 區塊的 fail key；錯誤訊息文字不抄寫，由 spec 的 Then 定義。「需確認」欄標的是刪除、送出、不可逆操作。

**狀態**：這是 Design 最常漏、也最常自己腦補的部分，五個項目（載入中、空資料、錯誤、無權限、資料狀態差異）全部要有，沒有的明確寫「不適用」而不是留白；腳本會檢查五項齊全（DS-04）。

**驗收條件**：每條要能對著畫面打勾。避免「應該清楚易懂」這類無法驗證的敘述。驗收條件是元件測試與 E2E 的來源，斷言主詞只能是畫面元素或「是否觸發 `uc-xxx`」，不寫領域狀態（那是 spec Scenario 的事）。

**待確認事項**：清空後寫「（無）」，段落本身不能省略。

### 明確不寫的東西

短規格裡**不要**出現以下內容，出現了就刪掉：

- 排版與位置（「放在右上角」「兩欄」）
- 元件選型（「用 Modal」「用 Tab」）——除非它是既有元件庫的命名
- 顏色、間距、字級、圖示
- 動畫與過場
- 文案的最終字句（可以寫「需要一句說明為什麼被拒絕」，不寫那句話本身；例外是 spec 已固定的錯誤／確認訊息，照抄）

這些交給 Claude Design 出第一版，再用 tweaks 調。如果使用者堅持要寫，記錄在「待確認事項」而不是規格本體，並註明「使用者偏好，非需求」。

## 提問策略

依畫面類型，優先問的東西不一樣：

| 類型   | 最先問                                                       |
| ------ | ------------------------------------------------------------ |
| 列表   | 預設排序、篩選條件、單筆點進去去哪、預估筆數                 |
| 表單   | 必填欄位、驗證時機（即時 / 送出時）、草稿要不要存、送出後去哪 |
| 詳情   | 哪些欄位可以在這裡直接改、狀態不同時操作差異                 |
| 儀表板 | 每個數字的定義與資料來源、時間範圍怎麼選、點擊後鑽取到哪     |
| 流程   | 步驟能否回頭、中途離開資料留不留、哪一步是不可逆的           |
| 對話框 | 為什麼不是獨立頁面、關閉後母畫面要不要刷新                   |

通用原則：

- 一次 3–5 題，先問會改變資訊架構的（進入離開、權限、拆不拆畫面），再問欄位層級的。
- 每題附理由，說明這個答案會影響畫面的哪個部分。
- 問題能給選項就給選項，並說出你的建議與原因。
- Spec 已經有答案的不要再問，直接填進去、在回覆裡註明「依 spec 的 `uc-xxx`」或「依欄位表 `xxx.yyy`」。

## 定案前檢查

### 由腳本檢查（`ui-check`，檢查 ID 見 `checks.md`）

- 畫面標題與八個段落標題符合固定格式（DS-01、DS-02）
- 資料表來源、操作表觸發、角色表、進入與離開引用的 ID 都存在於 spec 或本檔（REF-07、DS-03）
- 狀態段五項齊全（DS-04）
- 操作觸發的 Use Case 的 `roles` 與角色表一致（DS-05）
- 每個寫入 Use Case 至少被一個畫面引用（DS-06，warn）
- 每個畫面被其他畫面導向，或是模組入口（DS-07，warn）

### 人工判斷

每個畫面標「已定案」之前跑一次：

- **完整性**：每個操作都有失敗處理？每個角色都有對應的可見範圍？
- **一致性**：欄位的中文名稱跟 spec 名詞表一致？同一個操作在不同畫面叫同一個名字？狀態名稱跟 spec 一致？
- **可測試性**：每條驗收條件能對著畫面打勾？有沒有「合理」「清楚」「快速」這類模糊詞？
- **對齊後端**：畫面需要但欄位表沒有的欄位有沒有列在待確認事項？畫面會做但 spec 沒有的 Use Case 有沒有列出來？

發現 Spec 本身有問題（欄位缺、`fail` 不完整），列在畫面的待確認事項並標註「需回饋後端 Spec」，不要在 UI 規格裡自己補一個後端沒有的東西。

## 追溯矩陣

Feature → UseCase → Entity → Screen 的追溯矩陣**不手寫、不進版控**：`spec-check --report`（帶 ui 檔）或 `ui-check --report` 從解析結果即時印出，需要時貼進 PR 說明或會議紀錄。手寫的矩陣必然過期，腳本印的才是現況。

## 命名慣例

- Screen ID `s-<對象>-<型態或動作>`：`s-swimlane-list`、`s-card-edit`、`s-swimlane-delete-dialog`。一旦進入開發就不改名；要改視為移除 + 新增，走 CR。
- 移除的畫面直接刪掉整段；若還有其他畫面的「進入與離開」引用它，`ui-check` 會報 error，一併清掉。
- 畫面名稱用「對象 + 動作或型態」：泳道列表、卡片編輯、刪除 Swimlane 對話框。
- 操作名稱用動詞開頭，跟 spec 的 Use Case `name` 一致：刪除 Swimlane、設定顏色標記。
- 這些名稱會原封不動帶進 Design 提示詞和 handoff bundle，之後 Claude Code 生成的元件也會沿用，所以命名時當作在命名程式碼。

## Design 提示詞格式

畫面定案後，依短規格產出這段，直接貼進 Claude Design：

```markdown
# [Feature 名稱]：[畫面名稱]（s-<id>）

## 這個畫面的目的
（短規格的「目的」一句話）

## 使用者從哪來、往哪去
（進入與離開；Screen ID 換成畫面名稱）

## 角色差異
（角色與權限表，Role ID 換成角色名稱；沒有差異就寫「所有角色相同」）

## 要顯示 / 輸入的資料
（資料表，保留欄位名與驗證規則；來源欄可省略）

## 可以做的操作
（操作表，含確認與失敗處理；觸發欄換成操作名稱）

## 必須設計的狀態
載入中 / 空資料 / 錯誤 / 無權限 / [資料狀態差異]
每一種都要有畫面，不要只做正常狀態。

## 限制
- 使用既有元件庫：[有連 repo 就寫「以 repo 內元件為準」，沒有就寫「先用預設，之後對齊」]
- 不要新增規格以外的欄位或操作，覺得缺什麼在畫面旁邊註記，不要自行補上。
- 元件與區塊命名沿用上面的名稱。
```

貼之前確認兩件事：Claude Design 有沒有先 Import codebase（有既有專案一定要連），以及同一 Feature 的多個畫面是否一起貼、讓 Design 看得到畫面間的導覽關係。

## 交接到 Claude Code

Design 定稿後，Handoff bundle 的 README 由使用者自己補，不要用預設的。這份 Convention 在這一步只提供一件事：把該畫面的短規格原文附進 README，並標明「以此為準，設計稿與規格衝突時規格優先」。技術堆疊、檔案路徑、分層規則屬於工程慣例，不在這份文件範圍。
