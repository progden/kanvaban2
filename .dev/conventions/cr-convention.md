# 變更單規範（Change Request Convention）

> **本次修訂摘要**（對應 `.dev/prompts/improve-convention-prompt.md` 的設計決策）
>
> | 修訂處 | 對應決策 |
> |------|------|
> | 第 1 節：改名詞定義（實體／欄位／關係表）、角色定義、usecase 區塊一律開 CR | D5、D3 |
> | 第 3 節：CR 的影響範圍改為列出受影響的 ID（Entity、UseCase、Screen），腳本用它對照 PR diff | D5 |
> | 第 4.2 節：離開條件加「`spec-check`／`ui-check`／`cr-check` 通過」 | D1、D5 |
> | 第 6 節：總表新增「影響 ID」欄 | D5 |
> | 第 8 節：檢查清單標示哪些改由腳本檢查 | D1 |

本文件定義規格進入開發後，所有新增 / 變更 / 移除需求的處理方式。變更單（CR）是規格變更的唯一入口：沒有 CR 的變更不得進入規格文件。

與 `spec-convention.md` 的關係：本文件管「流程與狀態」，spec-convention 管「規格檔內怎麼寫」。CR 編號即規格檔中 `@CR-xxx` tag 的來源。

---

## 1. 什麼時候要開 CR

| 情況 | 是否開 CR |
|------|-----------|
| 規格尚未進入開發，SA 自行修訂 | 否，直接改 |
| 規格已進入開發（含開發中、已上線），要新增 Scenario | 是 |
| 規格已進入開發，要修改既有 Scenario 的行為 | 是 |
| 規格已進入開發，要移除既有 Scenario | 是 |
| 規格已進入開發，要修改「名詞定義」的實體／欄位／關係表、「角色定義」、或任何 Feature 的 usecase 區塊（含 `pre`／`post`／`fail`／`crud`／`roles`／`emits`／`requires`） | **是，一律開**。這些是腳本解析的結構，改了就改變開發者要做的事，即使沒有動到任何 Scenario 也算 |
| 規格已進入開發，要修改 `ui-<模組>.md` 的操作表（觸發的 Use Case）、角色與權限表、進入與離開 | 是 |
| 只是修錯字、調整措辭，不改行為，也不改任何 ID 或 usecase 區塊 | 否，直接 PR 並在說明註明「文字修正」 |
| 「其他名詞」表、「待釐清」段落、ui 檔的「目的」「驗收條件」「待確認事項」 | 否，直接改 |
| 待釐清項目有了結論要轉成 Scenario | 是 |

判斷原則：**會改變開發者要做的事**就開 CR。「已進入開發」以 spec 檔頭的 `狀態：開發中` 為準（`spec-convention.md` §2.1）。腳本解析的固定格式（三張名詞表、角色表、usecase 區塊、ui 的操作／角色／導覽）全部屬於「開發者要做的事」。

---

## 2. CR 編號與存放

- 編號格式：`CR-<三位數流水號>`，全專案共用一組流水號，不分模組。例：`CR-023`。
- 若使用票務系統（Jira / GitHub Issue），以票務系統編號為準，規格 tag 直接用該編號（例：`@KB-142`），不另外編 CR 號。
- **總表**：`.dev/CR.md`，記錄所有 CR（見第 6 節）。**每張 CR 都必須先在總表登記，才能在規格中掛上對應的 `@CR-xxx` tag**（見 `spec-convention.md` 第 5 節）；總表本身要能承載第 3 節列出的必填欄位，不依賴明細檔。`spec-check` 會檢查規格裡每個 `@CR-xxx` 都在總表（REF-06）。
- **明細檔**：`.dev/cr/CR-023.md`，一張 CR 一個檔案，**非必填**。只有需要記錄較長的背景說明、討論過程或多輪決議的 CR 才開明細檔，並在總表該筆的「明細」欄位連結過去；內容單純、影響範圍小的 CR，登記總表即可，不必開檔。

---

## 3. CR 內容模板

以下欄位是每張 CR 的**必填資訊**，一律先寫進總表 `.dev/CR.md`（見第 6 節）：狀態、類型、提出人、提出日期、影響模組、**影響 ID**、背景（一句話）、變更內容（一句話）、驗收標準。其餘（影響 Scenario、規格 PR、開發 PR、決議紀錄）可在後續階段補上，同樣寫在總表對應的欄位或區塊。

### 影響 ID

「影響 ID」列出這張 CR 會新增、修改或移除的 **Entity、UseCase、Screen** ID，全部反引號包住、以 `、` 分隔；新增的 ID 在後面加 `(新增)`，移除的加 `(移除)`，其餘視為修改。Attribute、Role、Event 不用列（它們隸屬於 Entity／UseCase，diff 到了自然會帶出所屬 ID）。

`cr-check` 在 CI 用這個欄位對照 PR diff：diff 裡被改到的 usecase 項目、實體表列、畫面段落所屬的 ID，必須跟這裡列的一致，**多改、少改都報 error**（CR-01）。改到的 Scenario 以它的 `@uc-` 決定所屬 UseCase ID。

只有需要更完整的背景說明、多輪決議討論時，才另外開明細檔。

**格式範例**（明細檔 `.dev/cr/CR-024.md`）：

```markdown
# CR-024：刪除含卡片的 Swimlane 改為轉移

| 欄位 | 內容 |
|------|------|
| 狀態 | 記錄 / 修改規格 / 待處理 / 處理完成 |
| 類型 | 新增 / 變更 / 移除 |
| 提出人 | |
| 提出日期 | |
| 影響模組 | spec-kanban-basic、ui-kanban-basic |
| 影響 Feature | Swimlane 管理 |
| 影響 ID | `swimlane`、`card`、`uc-delete-swimlane`、`s-swimlane-delete-dialog`(新增) |
| 影響 Scenario | （變更）刪除包含卡片的 Swimlane 需要確認 → 刪除包含卡片的 Swimlane 需要先轉移卡片；（新增）未選擇目的 Swimlane 時不可刪除包含卡片的 Swimlane |
| 依賴 CR | （無） |
| 規格 PR | #45 |
| 開發 PR | #52 |

## 背景／原因
為什麼要改。來自哪個模組、哪個使用情境的發現。

## 變更內容
用一段話描述行為上的差異。變更類的要寫「原本 → 改為」。
原本：刪除含卡片的泳道會連同卡片一併刪除。
改為：必須先指定目的泳道，卡片移過去後才刪除泳道（`uc-delete-swimlane` 的 `pre.p2`、`crud` 由 `card: D` 改為 `card: U`）。

## 影響範圍
- 是否影響其他模組或 Feature
- 是否影響既有資料（需要 migration 嗎）
- 是否影響已上線行為

## 驗收標準
條列可驗證的結果，之後會直接轉成 Scenario 的 Then。
- 刪除含卡片的泳道時，系統要求選擇目的泳道
- 未選目的泳道時顯示 "請選擇接收卡片的目的 Swimlane"，資料不變
- 選定後卡片移到目的泳道，原泳道刪除

## 決議紀錄
| 日期 | 內容 |
|------|------|
```

開了明細檔後，總表對應筆的背景／變更內容欄位可簡化寫「詳見明細」，並在「明細」欄連結過去；**「影響 ID」欄不得簡化**，總表與明細檔都要有且一致，`cr-check` 只讀總表。

## 4. 生命週期

CR 依序經過四個階段。每個階段有明確的進入條件、要做的事、以及進入下一階段的條件。

```
記錄 ──> 修改規格 ──> 待處理 ──> 處理完成
  │          │
  └── 駁回   └── 退回「記錄」
```

### 4.1 記錄

**目的**：先把需求抓下來，不遺漏，但還不動規格。

| 項目 | 內容 |
|------|------|
| 進入條件 | 任何人發現需要新增 / 變更 / 移除規格 |
| 負責人 | 提出人 |
| 要做的事 | 在總表 `.dev/CR.md` 新增一筆，填寫必填欄位（含影響 ID，可先填目前知道的）；狀態設為「記錄」；影響範圍複雜、需要長篇背景說明才另開明細檔 `.dev/cr/CR-xxx.md` |
| 規格檔 | **不動** |
| 離開條件 | SA / 架構師審核通過，確認要做 → 進入「修改規格」；確認不做 → 狀態改「駁回」並寫下原因 |

要點：
- 在做第三個模組時發現第一個模組要改，就在這個階段先開 CR，不要中斷手上的工作去改第一個模組的規格。
- 一張 CR 只處理一件事。發現三個要改的地方就開三張，方便獨立排程與追蹤。
- 影響 ID 在這個階段允許不完整，但進入「修改規格」前要補齊（`cr-check` 會擋）。

### 4.2 修改規格

**目的**：把 CR 轉成規格文件中的 Scenario 與 usecase 區塊，並掛好 tag。

| 項目 | 內容 |
|------|------|
| 進入條件 | CR 審核通過 |
| 負責人 | SA |
| 要做的事 | 依 spec-convention 第 5 節修改規格檔：新增 → `@added @wip @CR-xxx @uc-<id>`；變更 → 舊掛 `@deprecated @CR-xxx @uc-<id>`、新掛 `@changed @wip @CR-xxx @uc-<id>`；移除 → `@deprecated @CR-xxx @uc-<id>`。需要時同步改 usecase 區塊、名詞表、角色表、ui 檔。更新規格檔的「變更紀錄」。提規格 PR，PR 標題含 CR 編號 |
| 規格檔 | 修改中，PR 未合併 |
| 離開條件 | **`spec-check`、`ui-check`、`cr-check` 全部無 error**，且規格 PR review 通過並合併 → 進入「待處理」；review 發現需求本身有問題 → 退回「記錄」 |

要點：
- 規格 PR 的 reviewer 至少包含一位開發該模組的工程師，確保他知道有東西要改。reviewer 不重做腳本已檢查的項目，只看 `llm-review.md` 列的語意問題與 diff 本身。
- 總表（或明細檔，若已開）的「影響 Scenario」、「影響 ID」與「規格 PR」欄位在此階段補齊。`cr-check` 報「多改」代表 PR 動到了 CR 沒列的 ID：要嘛補進影響 ID，要嘛從 PR 拿掉；報「少改」代表 CR 列了但 PR 沒動：要嘛 PR 補上，要嘛從影響 ID 移除。

### 4.3 待處理

**目的**：規格已定案，等待開發排程與實作。

| 項目 | 內容 |
|------|------|
| 進入條件 | 規格 PR 已合併 |
| 負責人 | PM / Tech Lead 排程，開發者實作 |
| 要做的事 | 排入 sprint 或 backlog；開發者依 `@wip` Scenario 實作；開發 PR 標題含 CR 編號 |
| 規格檔 | 已合併，含狀態 tag |
| 離開條件 | 開發 PR 合併、驗收通過 → 進入「處理完成」 |

要點：
- 開發者用 `--tags "@CR-xxx"` 即可看到該 CR 的全部影響範圍；用 `spec-check --report` 可看該 CR 影響的 Use Case 碰到哪些實體、被哪些畫面引用。
- 若開發途中發現規格有缺漏，**不直接改規格**：在 CR 決議紀錄中註明，由 SA 判斷是補在同一張 CR（小修，退回「修改規格」）還是另開新 CR。

### 4.4 處理完成

**目的**：清理規格檔的狀態 tag，讓規格回到「只描述現況」的狀態。

| 項目 | 內容 |
|------|------|
| 進入條件 | 驗收通過 |
| 負責人 | SA |
| 要做的事 | 移除 `@wip` / `@added` / `@changed`；刪除 `@deprecated` Scenario；保留 `@CR-xxx`、`@uc-`、`@fail-`；提清理 PR（`spec-check` 仍要過）；在總表 `.dev/CR.md` 把該筆狀態改「處理完成」，填寫開發 PR 編號與完成日期 |
| 規格檔 | 只剩 `@CR-xxx`、`@uc-`、`@fail-` tag |
| 離開條件 | 終態 |

要點：
- 清理 PR 與開發 PR 分開，避免規格清理被夾在程式碼變更裡看不到。
- 「處理完成」的 CR 不再修改。若後續又要改同一處，開新 CR。

## 5. 狀態總表

| 狀態 | 規格檔狀態 | 誰在等誰 |
|------|-----------|----------|
| 記錄 | 未動 | 等 SA / 架構師審核 |
| 修改規格 | PR 進行中 | 等腳本檢查與規格 review |
| 待處理 | 已合併、有 `@wip` | 等排程 / 開發 / 驗收 |
| 處理完成 | 已清理、只剩 `@CR-xxx` 與 `@uc-`／`@fail-` | — |
| 駁回 | 未動 | — |

每個狀態轉換都要在 CR 的「決議紀錄」加一行：日期 + 轉到哪個狀態 + 原因（若有）。

`cr-check` 把狀態為「修改規格」與「待處理」的 CR 視為**進行中**；同一個 Scenario 不得同時被兩張進行中的 CR 掛 `@changed`（CR-02）。

## 6. CR 總表

`.dev/CR.md` 是所有 CR 的**唯一事實來源**：每張 CR 一律要在這裡登記，明細檔是選填的延伸，不是總表的替代品。每次狀態變更同步更新。`cr-check` 只讀這份總表，欄位順序與名稱固定如下。

**格式範例**（總表 `.dev/CR.md`）：

```markdown
# CR 總表

| 編號 | 標題 | 類型 | 提出人 | 提出日期 | 影響模組 | 影響 ID | 狀態 | 完成日期 | 明細 |
|------|------|------|--------|----------|----------|---------|------|----------|------|
| CR-023 | Swimlane 顏色標記 | 新增 | 王小明 | 2026-09-12 | spec-kanban-basic | `swimlane`、`uc-set-swimlane-color`(新增) | 待處理 | | |
| CR-024 | 刪除含卡片的 Swimlane 改為轉移 | 變更 | 王小明 | 2026-09-12 | spec-kanban-basic、ui-kanban-basic | `swimlane`、`card`、`uc-delete-swimlane`、`s-swimlane-delete-dialog`(新增) | 修改規格 | | [CR-024](cr/CR-024.md) |

### CR-023：Swimlane 顏色標記
- 背景：為什麼要改，一句話。
- 變更內容：原本 → 改為（或新增的行為）。
- 驗收標準：條列可驗證的結果。

### CR-024：刪除含卡片的 Swimlane 改為轉移
- 背景／變更內容／驗收標準：詳見明細 [CR-024](cr/CR-024.md)
```

主表格保留一覽用途（站立會議或規劃會議一眼看到哪些 CR 卡在哪個階段），每筆下方的區塊放必填的背景／變更內容／驗收標準；沒有開明細檔的 CR，這個區塊就是唯一記錄，務必填寫完整。已開明細檔的 CR，這裡可簡化寫「詳見明細」並連結。

「影響 Feature」欄由腳本從影響 ID 反查（UseCase 屬於哪個 Feature），總表不再手填；需要看時用 `spec-check --report`。

## 7. 常見情境

**做第三個模組時發現第一個模組要擴充**
開 CR（記錄）→ 繼續做第三個模組 → 第三個模組告一段落後，SA 集中審核累積的 CR → 逐張進入「修改規格」。

**開發者在實作時發現規格矛盾**
在 CR 決議紀錄留言 → SA 判斷 → 小修退回「修改規格」補一版；大改另開 CR，原 CR 繼續。

**同一個 Scenario 被兩張 CR 同時改**
後開的 CR 必須等前一張進入「處理完成」後才能進「修改規格」，避免 `@changed` 疊 `@changed`。在後開的 CR「依賴 CR」欄註明前一張的編號；`cr-check` 會擋兩張進行中 CR 同時掛 `@changed` 在同一個 Scenario（CR-02）。

**只改 usecase 區塊、沒動 Scenario**
例如把 `roles` 多加一個角色、`fail` 補一條。仍要開 CR、列影響 ID；若 `fail` 新增了 key，同一個 PR 要補對應的 `@fail-` Scenario（掛 `@added @wip @CR-xxx`），否則 `spec-check` 會報 UC-05。

**只改 ui 檔**
例如某個操作改由另一個畫面觸發。開 CR、影響 ID 列 Screen ID；不動 spec 就不需要掛任何 tag，`cr-check` 以 diff 裡的畫面段落對照。

**CR 做到一半決定不做**
狀態改「駁回」，若規格已合併 `@wip` Scenario，提 PR 移除並在變更紀錄註明「CR-xxx 取消」。

## 8. 檢查清單

### 由腳本檢查（`cr-check`，檢查 ID 見 `checks.md`）

- 影響 ID 與 PR diff 實際改動的 ID 一致（CR-01）
- 同一 Scenario 不被兩張進行中 CR 同時掛 `@changed`（CR-02）
- 規格裡每個 `@CR-xxx` 都在總表（REF-06，由 `spec-check` 報）
- tag 格式、順序、`@changed`／`@deprecated` 配對（GH-04，由 `spec-check` 報）

### 人工判斷

進入「修改規格」前：
- [ ] 已在總表 `.dev/CR.md` 登記，必填欄位齊全
- [ ] 驗收標準可轉成 Then 步驟（LLM review 項目，見 `llm-review.md`）
- [ ] 已確認不與進行中的 CR 衝突（同一 Use Case 或同一畫面）

進入「待處理」前：
- [ ] 三支腳本無 error
- [ ] 規格檔變更紀錄已追加
- [ ] 至少一位該模組開發者 review 過

進入「處理完成」前：
- [ ] 開發 PR 已合併、驗收通過
- [ ] 狀態 tag 已清除、`@deprecated` 已刪除，清理 PR 的 `spec-check` 通過
- [ ] 總表 `.dev/CR.md`（與明細檔，若有）狀態已更新為「處理完成」
