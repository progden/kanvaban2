# 變更單規範（Change Request Convention）

本文件定義規格進入開發後，所有新增 / 變更 / 移除需求的處理方式。變更單（CR）是規格變更的唯一入口：沒有 CR 的變更不得進入規格文件。

與 `spec-convention.md` 的關係：本文件管「流程與狀態」，spec-convention 管「規格檔內怎麼寫」。CR 編號即規格檔中 `@CR-xxx` tag 的來源。

---

## 1. 什麼時候要開 CR

| 情況 | 是否開 CR |
|------|-----------|
| 規格尚未進入開發，SA 自行修訂 | 否，直接改 |
| 規格已進入開發（含開發中、已上線），要新增 Scenario | 是 |
| 規格已進入開發，要修改既有 Scenario 的行為 | 是 |
| 規格已進入開發，要移除既有 Scenario | 是 |
| 只是修錯字、調整措辭，不改行為 | 否，直接 PR 並在說明註明「文字修正」 |
| Open Question 有了結論要轉成 Scenario | 是 |

判斷原則：**會改變開發者要做的事**就開 CR。

---

## 2. CR 編號與存放

- 編號格式：`CR-<三位數流水號>`，全專案共用一組流水號，不分模組。例：`CR-023`。
- 若使用票務系統（Jira / GitHub Issue），以票務系統編號為準，規格 tag 直接用該編號（例：`@KB-142`），不另外編 CR 號。
- **總表**：`.dev/CR.md`，記錄所有 CR（見第 6 節）。**每張 CR 都必須先在總表登記，才能在規格中掛上對應的 `@CR-xxx` tag**（見 `spec-convention.md` 第 5 節）；總表本身要能承載第 3 節列出的必填欄位，不依賴明細檔。
- **明細檔**：`.dev/cr/CR-023.md`，一張 CR 一個檔案，**非必填**。只有需要記錄較長的背景說明、討論過程或多輪決議的 CR 才開明細檔，並在總表該筆的「明細」欄位連結過去；內容單純、影響範圍小的 CR，登記總表即可，不必開檔。

---

## 3. CR 內容模板

以下欄位是每張 CR 的**必填資訊**，一律先寫進總表 `.dev/CR.md`（見第 6 節）：狀態、類型、提出人、提出日期、影響模組、背景（一句話）、變更內容（一句話）、驗收標準。其餘（影響 Scenario、規格 PR、開發 PR、決議紀錄）可在後續階段補上，同樣寫在總表對應的欄位或區塊。

只有需要更完整的背景說明、多輪決議討論時，才另外開明細檔。

**格式範例**（明細檔 `.dev/cr/CR-023.md`）：

```markdown
# CR-023：Swimlane 顏色標記

| 欄位 | 內容 |
|------|------|
| 狀態 | 記錄 / 修改規格 / 待處理 / 處理完成 |
| 類型 | 新增 / 變更 / 移除 |
| 提出人 | |
| 提出日期 | |
| 影響模組 | spec-kanban-basic |
| 影響 Feature | Swimlane 管理 |
| 影響 Scenario | （新增）為 Swimlane 設定顏色標記 |
| 規格 PR | #45 |
| 開發 PR | #52 |

## 背景／原因
為什麼要改。來自哪個模組、哪個使用情境的發現。

## 變更內容
用一段話描述行為上的差異。變更類的要寫「原本 → 改為」。

## 影響範圍
- 是否影響其他模組或 Feature
- 是否影響既有資料（需要 migration 嗎）
- 是否影響已上線行為

## 驗收標準
條列可驗證的結果，之後會直接轉成 Scenario 的 Then。

## 決議紀錄
| 日期 | 內容 |
|------|------|
```

開了明細檔後，總表對應筆的背景／變更內容欄位可簡化寫「詳見明細」，並在「明細」欄連結過去。

## 4. 生命週期

CR 依序經過四個階段。每個階段有明確的進入條件、要做的事、以及進入下一階段的條件。

```
記錄 ──> 修改規格 ──> 待處理 ──> 處理完成
  │          │
  └── 駁回   └── 退回「記錄」
```

### 4.1 記錄

**目的**：先把需求抓下來，不遺漏，但還不動規格。

| 項目 | 內容 |
|------|------|
| 進入條件 | 任何人發現需要新增 / 變更 / 移除規格 |
| 負責人 | 提出人 |
| 要做的事 | 在總表 `.dev/CR.md` 新增一筆，填寫必填欄位；狀態設為「記錄」；影響範圍複雜、需要長篇背景說明才另開明細檔 `.dev/cr/CR-xxx.md` |
| 規格檔 | **不動** |
| 離開條件 | SA / 架構師審核通過，確認要做 → 進入「修改規格」；確認不做 → 狀態改「駁回」並寫下原因 |

要點：
- 在做第三個模組時發現第一個模組要改，就在這個階段先開 CR，不要中斷手上的工作去改第一個模組的規格。
- 一張 CR 只處理一件事。發現三個要改的地方就開三張，方便獨立排程與追蹤。

### 4.2 修改規格

**目的**：把 CR 轉成規格文件中的 Scenario，並掛好 tag。

| 項目 | 內容 |
|------|------|
| 進入條件 | CR 審核通過 |
| 負責人 | SA |
| 要做的事 | 依 spec-convention 第 5 節修改規格檔：新增 → `@added @CR-xxx @wip`；變更 → 舊掛 `@deprecated @CR-xxx`、新掛 `@changed @CR-xxx @wip`；移除 → `@deprecated @CR-xxx`。更新規格檔的「變更紀錄」。提規格 PR，PR 標題含 CR 編號 |
| 規格檔 | 修改中，PR 未合併 |
| 離開條件 | 規格 PR review 通過並合併 → 進入「待處理」；review 發現需求本身有問題 → 退回「記錄」 |

要點：
- 規格 PR 的 reviewer 至少包含一位開發該模組的工程師，確保他知道有東西要改。
- 總表（或明細檔，若已開）的「影響 Scenario」與「規格 PR」欄位在此階段補齊。

### 4.3 待處理

**目的**：規格已定案，等待開發排程與實作。

| 項目 | 內容 |
|------|------|
| 進入條件 | 規格 PR 已合併 |
| 負責人 | PM / Tech Lead 排程，開發者實作 |
| 要做的事 | 排入 sprint 或 backlog；開發者依 `@wip` Scenario 實作；開發 PR 標題含 CR 編號 |
| 規格檔 | 已合併，含狀態 tag |
| 離開條件 | 開發 PR 合併、驗收通過 → 進入「處理完成」 |

要點：
- 開發者用 `--tags "@CR-xxx"` 即可看到該 CR 的全部影響範圍。
- 若開發途中發現規格有缺漏，**不直接改規格**：在 CR 決議紀錄中註明，由 SA 判斷是補在同一張 CR（小修，退回「修改規格」）還是另開新 CR。

### 4.4 處理完成

**目的**：清理規格檔的狀態 tag，讓規格回到「只描述現況」的狀態。

| 項目 | 內容 |
|------|------|
| 進入條件 | 驗收通過 |
| 負責人 | SA |
| 要做的事 | 移除 `@wip` / `@added` / `@changed`；刪除 `@deprecated` Scenario；保留 `@CR-xxx`；提清理 PR；在總表 `.dev/CR.md` 把該筆狀態改「處理完成」，填寫開發 PR 編號與完成日期 |
| 規格檔 | 只剩 `@CR-xxx` tag |
| 離開條件 | 終態 |

要點：
- 清理 PR 與開發 PR 分開，避免規格清理被夾在程式碼變更裡看不到。
- 「處理完成」的 CR 不再修改。若後續又要改同一處，開新 CR。

---

## 5. 狀態總表

| 狀態 | 規格檔狀態 | 誰在等誰 |
|------|-----------|----------|
| 記錄 | 未動 | 等 SA / 架構師審核 |
| 修改規格 | PR 進行中 | 等規格 review |
| 待處理 | 已合併、有 `@wip` | 等排程 / 開發 / 驗收 |
| 處理完成 | 已清理、只剩 `@CR-xxx` | — |
| 駁回 | 未動 | — |

每個狀態轉換都要在 CR 的「決議紀錄」加一行：日期 + 轉到哪個狀態 + 原因（若有）。

---

## 6. CR 總表

`.dev/CR.md` 是所有 CR 的**唯一事實來源**：每張 CR 一律要在這裡登記，明細檔是選填的延伸，不是總表的替代品。每次狀態變更同步更新。

**格式範例**（總表 `.dev/CR.md`）：

```markdown
# CR 總表

| 編號 | 標題 | 類型 | 提出人 | 提出日期 | 影響模組 | 影響 Feature | 狀態 | 完成日期 | 明細 |
|------|------|------|--------|----------|----------|--------------|------|----------|------|
| CR-023 | Swimlane 顏色標記 | 新增 | 王小明 | 2026-09-12 | spec-kanban-basic | Swimlane 管理 | 待處理 | | |
| CR-024 | 刪除含卡片的 Swimlane 改為轉移 | 變更 | 王小明 | 2026-09-12 | spec-kanban-basic | Swimlane 管理 | 修改規格 | | [CR-024](cr/CR-024.md) |

### CR-023：Swimlane 顏色標記
- 背景：為什麼要改，一句話。
- 變更內容：原本 → 改為（或新增的行為）。
- 驗收標準：條列可驗證的結果。

### CR-024：刪除含卡片的 Swimlane 改為轉移
- 背景／變更內容／驗收標準：詳見明細 [CR-024](cr/CR-024.md)
```

主表格保留一覽用途（站立會議或規劃會議一眼看到哪些 CR 卡在哪個階段），每筆下方的區塊放必填的背景／變更內容／驗收標準；沒有開明細檔的 CR，這個區塊就是唯一記錄，務必填寫完整。已開明細檔的 CR，這裡可簡化寫「詳見明細」並連結。

## 7. 常見情境

**做第三個模組時發現第一個模組要擴充**
開 CR（記錄）→ 繼續做第三個模組 → 第三個模組告一段落後，SA 集中審核累積的 CR → 逐張進入「修改規格」。

**開發者在實作時發現規格矛盾**
在 CR 決議紀錄留言 → SA 判斷 → 小修退回「修改規格」補一版；大改另開 CR，原 CR 繼續。

**同一個 Scenario 被兩張 CR 同時改**
後開的 CR 必須等前一張進入「處理完成」後才能進「修改規格」，避免 `@changed` 疊 `@changed`。在後開的 CR 影響範圍註明「依賴 CR-xxx」。

**CR 做到一半決定不做**
狀態改「駁回」，若規格已合併 `@wip` Scenario，提 PR 移除並在變更紀錄註明「CR-xxx 取消」。

---

## 8. 檢查清單

進入「修改規格」前：
- [ ] 已在總表 `.dev/CR.md` 登記，必填欄位齊全
- [ ] 驗收標準可轉成 Then 步驟
- [ ] 已確認不與進行中的 CR 衝突

進入「待處理」前：
- [ ] tag 符合 spec-convention 第 5 節
- [ ] `@changed` 有對應 `@deprecated`
- [ ] 規格檔變更紀錄已追加
- [ ] 至少一位該模組開發者 review 過

進入「處理完成」前：
- [ ] 開發 PR 已合併、驗收通過
- [ ] 狀態 tag 已清除、`@deprecated` 已刪除
- [ ] 總表 `.dev/CR.md`（與明細檔，若有）狀態已更新為「處理完成」
