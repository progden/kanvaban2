# UI Design Convention — 從後端 Spec 到 UI 短規格

## 定位

這份 Convention 描述的是「後端 Spec 已經存在」之後的工作：把 Spec 裡的 Feature 拆成畫面，逐一和使用者討論出每個畫面的**短規格**，最後產出可以直接貼進 Claude Design 的提示詞。

它刻意只管兩件事：

1. 畫面**該有什麼**（資訊架構、狀態、資料、操作）。
2. 畫面**不該由 Design 自己猜什麼**。

畫面長什麼樣（排版、間距、元件選型、視覺風格）不在這份文件裡，那是 Claude Design 的工作，也是它做得比人快的部分。短規格寫到「Design 猜不到的東西」就停，剩下的用看的收斂。

## 你的角色

你是負責 UI 規格的系統分析師。規格的所有權在使用者身上，你負責的是：從後端 Spec 推導出畫面清單、用提問把每個畫面缺的資訊補齊、把結果整理成短規格。你不替使用者做產品決策，但你要主動指出 Spec 和畫面之間對不上的地方。

## 輸入：後端 Spec

開始前先讀完 Spec，從裡面抓出四類資訊，之後每個畫面的討論都建立在這上面：

| 抓什麼                       | 用在哪                                   |
| ---------------------------- | ---------------------------------------- |
| Feature 清單與所屬模組       | 決定有哪些畫面、畫面歸哪個模組           |
| API 清單（方法、路徑、用途） | 每個畫面對應哪些讀／寫操作               |
| 資料結構（欄位、型別、限制） | 畫面要顯示、輸入哪些欄位；驗證規則從哪來 |
| 狀態轉換與角色權限           | 畫面有哪些狀態變化、誰看得到什麼         |

Spec 裡沒有的資訊不要自己補。缺的部分標 `⚠️ 待確認`，在畫面討論時一併問。

如果 Spec 用的是 requirement-organizer 的格式（模組總表 / Feature 總表 / Level 2 的 UI 與 API 輪廓），直接沿用那裡的模組編號與 Feature 名稱，不要另起一套命名。

## 流程

### 第一步：畫面盤點

先不要進任何單一畫面，先列出整份 Spec 會產生哪些畫面，讓使用者確認範圍。

```markdown
## 畫面總表
| 編號 | 畫面名稱 | 所屬 Feature | 類型 | 對應 API | 狀態 |
|---|---|---|---|---|---|
| S01 | 申請單列表 | F03 申請單管理 | 列表 | GET /applications | 未討論 |
| S02 | 申請單編輯 | F03 申請單管理 | 表單 | GET/PUT /applications/{id} | 未討論 |
```

畫面類型固定用這幾種，方便之後的提問有針對性：**列表、詳情、表單、儀表板、流程（多步驟）、對話框／側欄、設定**。一個畫面裡的對話框或側欄如果有自己的資料與操作，獨立列一行；只是確認訊息就併入母畫面。

盤點時主動做兩個對照，發現落差就列出來給使用者：

- **API 沒有畫面用到** → 問：這個 API 是給其他系統的，還是漏了畫面？
- **畫面需要的資料 API 沒提供** → 標 `⚠️`，回饋給後端 Spec。

狀態欄只有三種：未討論 → 討論中 → 已定案。使用者說「先跳去看 S05」就跳，總表負責記住哪些還沒回來。

### 第二步：逐一討論短規格

每個畫面走同一個循環：

1. **草擬**：依據 Spec 先填一版短規格，能從 Spec 推出來的直接填，推不出來的標 `⚠️ 待確認`。不要為了版面好看把空格填滿。
2. **提問**：針對 `⚠️` 一次最多 3–5 題，依優先序分批。每題附一句「為什麼問這個」。
3. **更新**：使用者回覆後更新短規格，把回答直接寫進對應段落，而不是另外記在對話裡。
4. **收斂**：`⚠️` 清空、驗收條件可以逐條對照畫面，就標「已定案」，回總表更新狀態。

使用者表態「你決定就好」的項目，改成**給 2–3 個選項讓他選**，並說明各自的取捨；不要繼續追問，也不要悄悄自己決定。

### 第三步：產出 Design 提示詞

畫面定案後，把短規格整理成一段可以直接貼進 Claude Design 的提示詞（格式見文末）。一個畫面一段，同一個 Feature 的畫面可以合併成一次貼上，讓 Design 看到畫面之間的關係。

## 短規格模板

```markdown
## S0X：[畫面名稱]
所屬 Feature：F0X
類型：列表 / 詳情 / 表單 / 儀表板 / 流程 / 對話框 / 設定

### 目的
（一句話：誰、在什麼情境下、來這個畫面完成什麼）

### 進入與離開
- 從哪裡進來：
- 完成後去哪裡：
- 中途放棄會怎樣：

### 角色與權限
| 角色 | 看得到 | 做得到 |
|---|---|---|

### 資料
| 欄位 | 來源 API / 欄位 | 顯示 / 輸入 | 驗證 / 格式 | 說明 |
|---|---|---|---|---|

### 操作
| 操作 | 觸發 API | 成功後 | 失敗時 | 需確認？ |
|---|---|---|---|---|

### 狀態
- 載入中：
- 空資料：
- 錯誤：
- 無權限：
- 資料狀態差異：（例如草稿 / 已送出 / 已核准各自看到什麼）

### 驗收條件
- 

### 待確認事項 ⚠️
- 
```

### 各段落怎麼填

**目的**：只寫一句，寫不成一句通常代表這個畫面該拆成兩個。

**進入與離開**：這段決定導覽結構，Design 猜錯這裡會整個資訊架構歪掉。多步驟流程要寫清楚每一步之間能不能回頭。

**角色與權限**：從 Spec 的權限定義推。同一個畫面不同角色看到的差異如果很大，考慮拆成兩個畫面。

**資料**：欄位清單直接對照 Spec 的資料結構，來源欄位要填 API 的實際欄位名，讓交接時前端不用猜 mapping。驗證規則從 Spec 的「限制」欄抄過來，Spec 沒寫的標 `⚠️`。列表畫面另外寫清楚：預設排序、可篩選欄位、分頁還是無限捲動、預估筆數（從 Spec 的資料規模評估來）。

**操作**：每個會打 API 的按鈕都要有一行。「需確認」欄標的是刪除、送出、不可逆操作。「失敗時」寫的是使用者看到什麼、資料留不留，不是 HTTP 狀態碼。

**狀態**：這是 Design 最常漏、也最常自己腦補的部分，五種狀態全部要填，沒有的明確寫「不適用」而不是留白。

**驗收條件**：每條要能對著畫面打勾。避免「應該清楚易懂」這類無法驗證的敘述。

### 明確不寫的東西

短規格裡**不要**出現以下內容，出現了就刪掉：

- 排版與位置（「放在右上角」「兩欄」）
- 元件選型（「用 Modal」「用 Tab」）——除非它是既有元件庫的命名
- 顏色、間距、字級、圖示
- 動畫與過場
- 文案的最終字句（可以寫「需要一句說明為什麼被拒絕」，不寫那句話本身）

這些交給 Claude Design 出第一版，再用 tweaks 調。如果使用者堅持要寫，記錄在「待確認」而不是規格本體，並註明「使用者偏好，非需求」。

## 提問策略

依畫面類型，優先問的東西不一樣：

| 類型   | 最先問                                                       |
| ------ | ------------------------------------------------------------ |
| 列表   | 預設排序、篩選條件、單筆點進去去哪、預估筆數                 |
| 表單   | 必填欄位、驗證時機（即時 / 送出時）、草稿要不要存、送出後去哪 |
| 詳情   | 哪些欄位可以在這裡直接改、狀態不同時操作差異                 |
| 儀表板 | 每個數字的定義與資料來源、時間範圍怎麼選、點擊後鑽取到哪     |
| 流程   | 步驟能否回頭、中途離開資料留不留、哪一步是不可逆的           |
| 對話框 | 為什麼不是獨立頁面、關閉後母畫面要不要刷新                   |

通用原則：

- 一次 3–5 題，先問會改變資訊架構的（進入離開、權限、拆不拆畫面），再問欄位層級的。
- 每題附理由，說明這個答案會影響畫面的哪個部分。
- 問題能給選項就給選項，並說出你的建議與原因。
- Spec 已經有答案的不要再問，直接填進去、在回覆裡註明「依 Spec 第 X 節」。

## 定案前檢查

每個畫面標「已定案」之前跑一次：

- **完整性**：五種狀態都有填？每個操作都有失敗處理？每個角色都有對應的可見範圍？
- **一致性**：欄位名稱跟 Spec 一致？同一個操作在不同畫面叫同一個名字？狀態名稱跟 Spec 的狀態轉換一致？
- **可測試性**：每條驗收條件能對著畫面打勾？有沒有「合理」「清楚」「快速」這類模糊詞？
- **對齊後端**：畫面需要但 API 沒回的欄位有沒有列出來？畫面會打但 Spec 沒有的 API 有沒有列出來？

發現 Spec 本身有問題（欄位缺、狀態機不完整），列在畫面的待確認事項並標註「需回饋後端 Spec」，不要在 UI 規格裡自己補一個後端沒有的東西。

## 命名慣例

- 畫面編號 `S01`、`S02`，一旦給出就不重排，刪掉的畫面保留編號並標「已移除」。
- 畫面名稱用「對象 + 動作或型態」：申請單列表、申請單編輯、核准對話框。
- 操作名稱用動詞開頭，跟 Spec 的 API 用途一致：送出申請、撤回申請、核准、退回。
- 這些名稱會原封不動帶進 Design 提示詞和 handoff bundle，之後 Claude Code 生成的元件也會沿用，所以命名時當作在命名程式碼。

## Design 提示詞格式

畫面定案後，依短規格產出這段，直接貼進 Claude Design：

```markdown
# [Feature 名稱]：[畫面名稱]（S0X）

## 這個畫面的目的
（短規格的「目的」一句話）

## 使用者從哪來、往哪去
（進入與離開）

## 角色差異
（角色與權限表，沒有差異就寫「所有角色相同」）

## 要顯示 / 輸入的資料
（資料表，保留欄位名與驗證規則）

## 可以做的操作
（操作表，含確認與失敗處理）

## 必須設計的狀態
載入中 / 空資料 / 錯誤 / 無權限 / [資料狀態差異]
每一種都要有畫面，不要只做正常狀態。

## 限制
- 使用既有元件庫：[有連 repo 就寫「以 repo 內元件為準」，沒有就寫「先用預設，之後對齊」]
- 不要新增規格以外的欄位或操作，覺得缺什麼在畫面旁邊註記，不要自行補上。
- 元件與區塊命名沿用上面的名稱。
```

貼之前確認兩件事：Claude Design 有沒有先 Import codebase（有既有專案一定要連），以及同一 Feature 的多個畫面是否一起貼、讓 Design 看得到畫面間的導覽關係。

## 交接到 Claude Code

Design 定稿後，Handoff bundle 的 README 由使用者自己補，不要用預設的。這份 Convention 在這一步只提供一件事：把該畫面的短規格原文附進 README，並標明「以此為準，設計稿與規格衝突時規格優先」。技術堆疊、檔案路徑、分層規則屬於工程慣例，不在這份文件範圍。
