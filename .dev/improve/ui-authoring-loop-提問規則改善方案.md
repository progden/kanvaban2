## 修改方案（依 LLM 比例 / 可程式化程度分三層）

### 方案 A — 純提示詞層（LLM 比例 100%，可程式化 0%）

只改 `ui-authoring-prompt.md` 文字，靠 loop 自己讀規則、自己自律，不加任何檢查腳本。

- 補 C1：矛盾類 OQ 固定要求三個選項（保留A／保留B／缺區分條件），寫進 `ui-authoring-open-questions.md`【矛盾】格式段。
- 補 E1：禁止事項新增一條「OQ／待確認事項不得出現說服性字眼（應該、建議這樣比較好、我認為）」。
- 補 E2：待確認事項與 OQ 情況欄前面固定加 `[Level: 模組/uc/scenario]` 標記。
- 補 B2：新增 Screen 前，先查 `ui-authoring-tasks.md` 與既有 ui 檔是否已有相同/被否決過的拆分決定。
- 補 C2：新增 OQ 前，先掃過既有 OQ 表與各 ui 檔「待確認事項」，同一 uc/entity 已有紀錄時要嘛不重開、要嘛明講「推翻先前 OQ-xx」。

成本：改文字，幾分鐘。風險：跟現有規則一樣完全依賴 loop 自律，沒有東西會真的擋下它漏做。

### 方案 B — 格式層 lint 腳本（LLM 比例中，可程式化中～高）

在 `.dev/loops/ui-authoring-loop/` 底下新增 loop 自己的檢查腳本（不動 `scripts/**`，那是禁區），純做「格式」層面的 regex 檢查，loop 每輪收尾必須跑過、不過不能算完成：

- 每筆新增 OQ 列，「情況」欄必須以 `【引用原文】`／`【矛盾】`／`【推論】`／`【覆蓋】` 開頭之一。
- 【覆蓋】列必須同時含「原文：」「→」「新文：」（或等義字串）。
- 【矛盾】列必須恰好列出三個選項關鍵字（保留、缺區分條件）。
- OQ／待確認事項全文掃描禁用詞清單（應該、我認為、建議這樣比較好）。
- 每個待確認事項行是否有 `[Level: ...]` 前綴。

成本：~80 行 lint script（Python 或 bash+grep），loop 收尾多一步「跑 lint，非 0 視為本輪未完成」。風險低：只抓格式漏做，抓不到「引用是不是真的沒改字」。

### 方案 C — 語意層交叉驗證（LLM 比例低～中，可程式化高，工程量較大）

在方案 B 基礎上加深到能核對「內容是否為真」，這是 lesson-learned 裡最容易被 LLM 悄悄違反、也最值得程式化的兩點：

1. **驗證「逐字引用」真的逐字**（對應 A1／C3 核心風險：LLM 假裝引用、其實已改寫）：lint script 把 OQ／待確認事項裡「」引號內文字，去 `spec-<模組>.md`（純文字比對，不需 parser）grep 是否存在完全相同子字串，抓不到就判定違規。
2. **驗證「完整類別總表」真的完整**（對應 B1）：OQ「選項」欄提到某類別（例如角色）時，重用 `scripts/speccheck` 的 parser（唯讀 import，不修改 `scripts/**`）解析對應 spec 的角色表，數角色總數跟 OQ 列出項目數比對，少了就判定不完整。
3. **重複提問偵測**（對應 C2）：對每筆新 OQ，用 uc/entity ID＋關鍵字做簡單 hash／字串相似度，跟既有 OQ 表比對，疑似重複就要求 loop 在情況欄加註「與 OQ-xx 的差異」。

成本：中～高，需一支 Python 腳本、讀 spec 純文字或借用既有 parser，估計半天到一天。這層才是真正把 lesson-learned 的不變量變成硬約束，尤其 A1/C3 逐字引用檢查直接對應 lesson-learned 第 9 點「AI 默默改掉」；1、2 兩項恰好對應 lesson-learned 第 6 節講的兩個根因（斷言缺來源、選項空間被截斷）。

## 初步建議（已採納，見上方「決定」）

方案 A 成本最低但約束力弱，只是把君子協定寫得更細。實際採用範圍比初步建議更廣：**方案 A 全部做 ＋ 方案 B 全部做 ＋ 方案 C 只做「逐字引用驗證」一項**；方案 C 的「類別總表計數」「重複提問偵測程式化」先跳過，之後真的常出問題再加。
